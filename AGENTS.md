# RX Repository Agent Guide

This file defines the repository-wide instructions for agents working on RX. Preserve existing user changes, keep edits scoped to the requested task, and treat source code as the final authority when documentation and implementation disagree.

## Mandatory Workflow

- Read and write text and source files as UTF-8 without BOM. Preserve LF line endings.
- Inspect the relevant code, tests, CMake files, and `.memory/` records before changing behavior.
- Use `rg` or `rg --files` for repository searches when available.
- Do not overwrite or revert unrelated user changes in a dirty worktree.
- Ask for explicit human confirmation before running any configure, build, or test command that triggers a build. Do not interpret a request to edit code as build authorization.
- Report code-review results in Chinese as copyable Markdown. Lead with findings, ordered by severity, and include concrete file paths and line numbers.
- State which validation was run and which validation was skipped. If the build was not authorized, say so explicitly.

## Project Overview

RX is a C++20 ReactiveX library inspired by RxJava and RxJS. It provides asynchronous programming through Observable streams and depends on:

- `gany` for type erasure and `GAny` values.
- `gx` for cross-platform utilities and scheduling support.

CMake fetches these dependencies into `deps/` when they are unavailable locally.

## Repository Map

- `rx/include/rx/`: public headers and core interfaces.
- `rx/include/rx/operators/`: Observable operator implementations.
- `rx/src/`: non-template implementation sources, including `observable.cpp`.
- `tests/`: primary GoogleTest unit and regression tests.
- `examples/`: optional comprehensive example executable (`TestRx`).
- `cmake/`: dependency and build helpers.

## Build and Validation

### Prerequisites

- CMake 3.20 or newer.
- A C++20 compiler: Clang 10+, GCC 10+, or MSVC 19.28+.
- Git and network access when CMake must fetch dependencies.

### Configure and Build

Only run these commands after explicit human confirmation. Always use a dedicated out-of-source directory.

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug -DBUILD_RX_TESTS=ON
cmake --build build --config Debug
```

`BUILD_RX_TESTS` defaults to `ON`. Enable the optional examples only when they are needed:

```bash
cmake -S . -B build -DBUILD_RX_TESTS=ON -DBUILD_RX_EXAMPLES=ON
```

### Primary Test Suite

The primary test target is `test_rx`, registered with CTest from `tests/CMakeLists.txt`.

```bash
ctest --test-dir build -C Debug --output-on-failure
```

To run the executable directly, use the path generated by the active CMake generator. With this repository's output settings it is normally:

```text
build/bin/test_rx
build/bin/test_rx.exe
```

### Optional Comprehensive Example

When configured with `-DBUILD_RX_EXAMPLES=ON`, CMake builds `TestRx` from `examples/test_rx.cpp`:

```text
build/bin/TestRx
build/bin/TestRx.exe
```

`TestRx` runs its test functions sequentially in `main()`. For temporary focused debugging, comment out unrelated calls, rebuild with authorization, run the executable, and restore the temporary edits before finishing. Do not commit a narrowed `main()` unless the task intentionally restructures the runner.

## Code Style

### Formatting

- Use 4 spaces; never use tabs.
- Use LF line endings.
- Put class and function opening braces on the next line (Allman style).
- Keep control-flow and lambda opening braces on the same line (K&R/OTBS style).

```cpp
void runTask()
{
    if (ready) {
        Observable::create([](const auto &emitter) {
            // ...
        });
    }
}
```

### Class Layout

Place constructors, destructors, and copy/move operations in the first `public` section. Put other public methods in a second `public` section.

```cpp
class Example
{
public:
    Example();
    ~Example();

public:
    void doSomething();
};
```

### Naming

- Classes and structs: `PascalCase`.
- Methods, functions, and variables: `camelCase`.
- Files: `snake_case`.
- Generic template types: `T`, `R`, `U`; use `Source` for observable sources.
- Macros: `UPPER_SNAKE_CASE`.
- Smart-pointer aliases: names ending in `Ptr`, such as `ObserverPtr`.

### Includes and Namespaces

For `.cpp` files, order includes as follows:

1. Associated header.
2. Local `rx/` headers.
3. `gx/` or `gany/` dependency headers.
4. Standard-library headers.

Use header guards following the `RX_PATH_FILENAME_H` pattern. Public code belongs in `namespace rx`. Never place `using namespace` in a header.

### Types and Ownership

- Target C++20.
- Prefer explicit types in public headers; use `auto` where it improves clarity for complex implementation types.
- Prefer fixed-width integers such as `int32_t` when the width matters.
- Allocate shared objects with `std::make_shared`.
- Use `std::weak_ptr` to break cycles, especially when callbacks stored by an object refer back to that object.
- Do not capture a `shared_ptr` by value in a lambda stored by the same object.
- Avoid holding locks while calling user code, including `onNext`, `onError`, and `onComplete`.

## Architecture and Implementation

### Core Components

- `Observable`: stream creation and operator API.
- `Observer`: receives `onNext`, `onError`, and `onComplete` signals.
- `Disposable`: controls cancellation and subscription lifetime.
- `Scheduler`: controls where and when work executes.
- `GAny`: type-erased value passed through streams.

### Implementing an Observable Operator

Use existing neighboring operators as the primary pattern. A typical operator change includes:

1. Add `rx/include/rx/operators/observable_<name>.h`.
2. Implement the operator Observable and its Observer behavior, with termination and disposal handled explicitly.
3. Declare the public method in `rx/include/rx/observable.h`.
4. Include the operator header and implement the factory method in `rx/src/observable.cpp`.
5. Add focused coverage under `tests/`; add or update `examples/test_rx.cpp` only when the comprehensive example also needs coverage.
6. Ensure terminal paths release Observer and Disposable chains.

### Error and Signal Handling

- Do not throw exceptions from `onNext` into downstream user code.
- Convert operator failures to `GAnyException` and deliver them through `onError`.
- If operator setup fails, notify the downstream Observer with `onError`.
- Respect the Observable contract: no signals after termination or disposal, and only one terminal signal.
- Do not hold internal locks while invoking downstream or user callbacks.

### Scheduling and Initialization

- Call `initGAnyCore()` before using RX in standalone executables.
- Set a global `GTimerScheduler` before relying on `MainThreadScheduler` or timer-based behavior.
- Keep asynchronous lifetimes explicit and ensure cancellation prevents later delivery.

### Leak Detection

- The repository uses `LeakObserver` to detect retained Observer chains.
- Comprehensive tests must finish with `LeakObserver::checkLeak()` where that runner expects it.
- Break reference cycles and dispose resources on completion, error, and cancellation.

## Testing Expectations

- Add the smallest focused regression test that fails before a bug fix and passes after it.
- Cover normal completion, error propagation, disposal, and scheduler-sensitive behavior when relevant.
- Avoid sleeps when deterministic scheduler control or synchronization is available.
- Keep tests isolated; restore global schedulers and other global state after each test.
- Do not weaken or delete existing assertions merely to make a change pass.

## Battle Memory

Use the battle-memory skill automatically for feature work, bug fixes, refactors, documentation maintenance, handoffs, cross-context continuation, and tasks that produce durable project knowledge.

At task start, read only the relevant `.memory/` records and project docs needed for the current decision. During work, keep task-relevant dialogue, decisions, source paths, validation results, and follow-ups in mind. Before finishing, create or update a focused `.memory/` record when the task produced durable knowledge.

Store memory in `.memory/`. Keep records concise, searchable, and tied to concrete source paths or docs. Do not store secrets, credentials, raw `.env` values, private personal data, or unnecessary raw chat logs; record redacted operational notes instead.
